## 2. 项目背景

学术成果数据分散在开放学术数据库、预印本平台、科研机构网站和其他公开数据源中，不同来源在字段命名、作者标识、机构名称、成果类型和更新时间等方面存在差异。单纯保存网页抓取结果难以支持统一检索、成果统计、作者合作分析和引用关系分析。

本系统拟建设一套面向学术成果元数据的采集、治理、存储、检索和可视化平台，通过可插拔的数据源适配器采集合法授权的数据，经过标准化、去重和实体消歧后，将业务权威数据保存到 MySQL，并将适合关系分析的数据同步到 Neo4j，最终提供成果查询、统计分析和知识图谱浏览能力。

## 3. 建设目标

### 3.1 总体目标

1. 建立统一、可追溯的学术成果元数据目录。
2. 支持多数据源的定时增量采集和人工触发采集。
3. 对成果、作者、机构、期刊或会议、主题和引用关系进行标准化管理。
4. 支持成果检索、统计分析和关系图谱可视化。
5. 保证采集任务可恢复、数据写入幂等、异常可追踪。
6. 在不绕过访问控制的前提下，遵守数据源规则和使用条款。
7. 为后续扩展专利、项目、奖项、著作、软件和数据集预留边界。

### 3.2 成功标准

- 任意成果记录可以追溯到原始数据源、来源记录标识和采集时间。
- 同一来源记录重复采集不会产生重复业务记录。
- 使用 DOI 等稳定标识能够自动识别重复成果。
- 采集任务中断后能够从检查点继续执行。
- MySQL 与 Neo4j 的同步失败可以定位、重试和补偿。
- 用户能够从统计图表或知识图谱进入成果详情。
- 系统能够在建议规模下满足第 10 节规定的性能指标。

## 4. 用户与使用场景

### 4.1 用户角色

| 角色 | 主要职责 | 核心权限 |
| --- | --- | --- |
| 系统管理员 | 维护系统、账号和数据源 | 用户与角色管理、数据源配置、系统参数、审计查看 |
| 数据运营人员 | 负责采集任务和数据质量 | 创建任务、重试任务、查看日志、处理重复候选、修正数据 |
| 科研用户 | 查询和分析成果 | 成果检索、统计分析、图谱浏览、数据导出 |

如系统仅用于个人课题或毕业设计，可以在第一阶段合并系统管理员与数据运营人员，但权限模型仍保留角色边界。

### 4.2 典型使用场景

1. 数据运营人员配置 OpenAlex 和 Crossref 数据源。
2. 系统按照计划拉取指定时间范围、机构、作者或主题的增量数据。
3. 系统解析来源记录并生成统一成果模型。
4. 系统根据 DOI、来源标识和内容指纹进行去重。
5. 数据运营人员处理系统无法确定的作者或成果合并候选。
6. 系统将确认后的实体和关系异步同步到 Neo4j。
7. 科研用户按作者、机构、年份、类型、主题等条件查询成果。
8. 科研用户查看作者合作网络、机构合作网络、引用关系和研究主题分布。
9. 管理员查看任务失败率、数据质量和图同步积压情况。

## 5. 范围定义

### 5.1 第一阶段 MVP 范围

第一阶段建议支持以下成果和实体：

- 期刊论文；
- 会议论文；
- 预印本；
- 作者；
- 作者所属机构；
- 期刊或会议；
- 关键词与研究主题；
- 论文引用关系；
- 作者合作关系；
- 机构合作关系。

第一阶段建议支持以下数据内容：

- 标题；
- 摘要（仅在来源许可范围内）；
- DOI、OpenAlex ID、来源原生 ID 等标识；
- 作者及作者顺序；
- 作者 ORCID；
- 作者机构；
- 发表或公开日期；
- 成果类型；
- 期刊、会议、卷期页码；
- 关键词和主题；
- 引用数量及可获得的引用关系；
- 原始来源、来源地址、采集时间和更新时间。

第一阶段只实现 OpenAlex 和 Crossref 两个结构化数据源适配器，优先顺序为 OpenAlex、Crossref。arXiv、OAI-PMH 和机构公开网页不纳入第一阶段开发范围。

### 5.2 后续阶段候选范围

- 专利；
- 科研项目；
- 科研奖励；
- 学术著作；
- 软件著作权；
- 开源软件；
- 科研数据集；
- 学者画像和影响力指标；
- 相似成果推荐；
- 全文检索或语义检索；
- 多机构租户隔离；
- 大规模分布式采集。

### 5.3 明确不纳入第一阶段

- 绕过登录、验证码、付费墙、IP 限制或其他访问控制；
- 未获授权的论文 PDF 全文下载和长期保存；
- 自动生成学术评价结论或排名结论；
- 使用单一指标自动判定研究人员水平；
- 微服务拆分、消息队列和分布式调度；
- Elasticsearch、OpenSearch 或向量数据库；
- 移动端原生应用；
- 对外开放的公共采集代理服务。

## 7. 核心业务规则

| 编号 | 规则 |
| --- | --- |
| BR-001 | MySQL 是业务权威数据源，Neo4j 是图查询投影。 |
| BR-002 | MySQL 写入成功而 Neo4j 同步失败时，成果仍然有效，但必须记录待重试事件。 |
| BR-003 | 数据源停用只阻止新任务，不自动删除已经采集的成果。 |
| BR-004 | 原始来源记录和标准成果分开保存，解析规则升级后可以重新处理原始记录。 |
| BR-005 | 自动合并必须记录合并依据和置信度。 |
| BR-006 | 人工确认结果优先于后续自动匹配结果，除非人工撤销。 |
| BR-007 | 删除成果默认采用逻辑删除，并同步移除或失效对应图投影。 |
| BR-008 | 外部引用数量属于来源快照，不作为永久不变的事实。 |
| BR-009 | 图谱中的作者合作关系由共同成果推导，不作为独立权威数据。 |
| BR-010 | 所有时间使用 UTC 保存，前端按用户或系统时区显示。 |

## 8. 数据需求

### 8.1 数据质量要求

- DOI 去除协议前缀、统一大小写并进行格式校验。
- ORCID 使用标准格式校验，但格式合法不等于身份已经确认。
- 标题必须保存原始值和标准化匹配值。
- 作者顺序必须保留。
- 机构别名与标准机构分开管理。
- 来源缺失字段不能使用虚构值填补。
- 数据冲突必须记录来源和处理策略。
- 统计分析不得将未知值静默归入其他明确类别。

### 8.2 数据追溯要求

每条标准成果至少能够追溯以下信息：

- 数据源；
- 来源记录 ID；
- 来源 URL 或 API 定位信息；
- 首次采集时间；
- 最近采集时间；
- 原始元数据摘要或快照；
- 解析器版本；
- 最近一次标准化结果；
- 自动或人工合并记录。

### 8.3 数据保留建议

- 标准成果、作者、机构和关系：长期保存，按业务规则逻辑删除。
- 原始元数据：保存 90 天。
- 普通运行日志：建议保存 30 天。
- 审计日志：建议保存 180 天或按组织制度执行。
- 失败记录：问题关闭后至少保存 90 天。

## 9. 合规与安全要求

1. 数据源必须有明确的公开接口、开放许可或组织授权依据。
2. 采集器必须遵守 robots.txt、接口频率限制和来源使用条款。
3. 系统不得提供绕过验证码、登录、付费墙或反爬访问控制的能力。
4. API 密钥、账号密码和令牌不得写入代码仓库。
5. 数据源 URL 必须经过协议、主机和目标地址校验，防止服务端请求伪造。
6. 解析的 HTML、JSON、XML 和文本均视为不可信输入。
7. 导出操作必须受权限控制并记录审计。
8. 用户密码必须使用强密码哈希保存。
9. Cookie 应使用 HttpOnly、SameSite 和生产环境 Secure 属性。
10. 前端展示外部文本时必须防止跨站脚本注入。
11. 摘要、作者信息和其他数据的展示与再利用必须遵守来源许可。
12. 本系统不对数据采集合规性作法律结论，正式上线前应由数据使用方完成合规审查。

## 10. 非功能需求

### 10.1 性能

以下指标基于“10 万条成果、100 万条图关系、单实例应用”的建议规模：

| 编号 | 指标 |
| --- | --- |
| NFR-PERF-001 | 普通成果列表和详情查询在正常负载下 P95 不超过 2 秒。 |
| NFR-PERF-002 | 300 个节点以内的局部图查询在正常负载下 P95 不超过 3 秒。 |
| NFR-PERF-003 | 列表接口默认每页 20 条，最大每页 100 条。 |
| NFR-PERF-004 | 图查询默认 100 个节点，硬上限 300 个节点。 |
| NFR-PERF-005 | 批处理必须分块提交，不得将整批数据一次性加载到内存。 |

### 10.2 可靠性

| 编号 | 指标 |
| --- | --- |
| NFR-REL-001 | 同一来源记录重复处理结果必须幂等。 |
| NFR-REL-002 | 任务异常退出后可以从最近成功检查点恢复。 |
| NFR-REL-003 | 网络重试必须有最大次数和退避，不允许无限重试。 |

| NFR-REL-006 | 数据库连接、HTTP 响应和文件资源必须被可靠释放。 |

### 10.3 可维护性

- 数据源使用统一适配器接口，并分别维护解析代码和测试样例。
- 业务模块之间通过明确的应用服务或事件通信。
- 数据库结构变更统一使用 Flyway。
- 后端接口通过 OpenAPI 描述。
- 关键规则必须有自动化测试。
- 不得在控制器中直接实现采集、去重或图同步逻辑。

### 10.4 可观测性

- 使用结构化日志。
- 关键日志包含 traceId、taskId、runId、sourceId。
- 采集、解析、标准化、持久化和图同步分别统计成功数、失败数和耗时。
- 对任务连续失败、解析成功率异常、图同步积压和数据库不可用提供告警依据。
- 健康检查区分应用存活和依赖就绪状态。

### 10.5 兼容性与部署

- 第一阶段只面向 Windows 本地开发和验收，不进行服务器部署。
- 后端和前端在本机直接运行，使用本机已安装的 MySQL80 服务。
- Neo4j 5.26 Community Edition 使用本地 Docker 容器运行。
- 本地仅允许 localhost 或经用户确认的同一内网访问，可以使用 HTTP。
- 未来部署到服务器时必须重新确认资源、网络和域名，并启用 HTTPS。
- 后端统一使用 Java 21。
- 本地 MySQL 使用已验证的 MySQL Community Server 8.0.42，端口为 3306；项目数据库使用 utf8mb4 字符集。
- Neo4j 基线使用 5.26 LTS，不使用已结束支持的 4.4。
- 浏览器建议支持最近两个主要版本的 Chrome 和 Edge。

### 10.6 阶段 4 实现边界与需求追溯

截至 2026-09-02，阶段 4 已在阶段 3 单源闭环上完成 OpenAlex/Crossref 双来源接入和 MySQL 数据治理，关闭以下当前阶段需求：

- `FR-SOURCE-001` 至 `FR-SOURCE-005`：两个来源均使用固定官方基础地址、独立受控配置、探测、启停和请求限制；
- `FR-TASK-001` 至 `FR-TASK-008`：两个来源复用同一任务状态机、Quartz、Spring Batch、检查点、暂停/恢复/取消和有限重试；OpenAlex 使用滚动发表日期窗口，Crossref 使用封闭索引日期窗口；
- `FR-CRAWL-001` 至 `FR-CRAWL-008`：Crossref 使用不透明游标、固定参数链、响应上限、限流和有限重试；解析异常、字段缺失和总量不一致均可定位，JATS/HTML 摘要不写入标准摘要字段；
- `FR-DATA-001` 至 `FR-DATA-010`：DOI、ORCID、ROR、ISSN 等稳定标识允许确定性关联并记录规则版本；无 DOI、无 ORCID、同名作者和纯文本机构只生成候选，不按名称或未经验证的模糊阈值自动合并；人工决定和字段修正可追溯、可受控撤销；
- `FR-CATALOG-001` 至 `FR-CATALOG-003`：规范目录按固定且与导入顺序无关的字段优先级聚合两个来源，详情展示字段来源、人工覆盖状态和双源追溯；

## 11. MVP 验收标准

### 11.1 业务验收

1. 至少完成两个结构化开放数据源适配器。
2. 能够创建一次性任务和每日增量任务。
3. 能够完成从采集、解析、标准化、去重到 MySQL 保存的完整流程。
4. 对相同来源数据重复运行任务，不产生重复成果。
5. 能够按标题、作者、机构、年份、类型和来源组合检索。
6. 能够展示成果详情及来源追溯信息。
7. 能够将成果、作者、机构、载体、主题和引用关系同步到 Neo4j。
8. 能够展示成果关系图、作者合作图和机构合作图。
9. 能够展示成果趋势、类型分布、机构分布和主题分布。
10. 能够查看任务失败原因并重试失败记录。

### 11.2 技术验收

1. 关键接口、任务、去重和图同步规则具备自动化测试。
2. 使用 Testcontainers 验证 MySQL 和 Neo4j 集成。
3. Flyway 能从空数据库完整创建结构。
4. 图同步重复执行不会创建重复节点或关系。
5. 应用重启后，未完成任务和未完成同步事件可以恢复。
6. 日志中不存在明文密码、令牌和数据源凭据。
7. 本地 MySQL80、Neo4j Docker 容器、Spring Boot 后端和 Vue 前端可以完成联合启动和连通性验证。
8. 备份和恢复步骤经过一次非生产环境演练。

## 12. 约束、依赖与风险

### 12.1 约束

- 后端使用 Java 和 Spring Boot。
- 使用 MySQL 保存业务权威数据。
- 第一阶段使用本机 MySQL80，即 MySQL Community Server 8.0.42，端口 3306；开发时创建独立的 aacv_system 数据库。
- MySQL 数据交互使用 MyBatis，不再采用 Spring Data JPA。
- MySQL 表、索引、约束和必要基础数据的版本迁移使用 Flyway。
- 使用 Neo4j 支撑知识图谱查询。
- Neo4j 数据交互使用 Spring Data Neo4j。
- 第一阶段保持模块化单体，不提前拆分微服务。
- 不在需求未确认前增加搜索引擎、消息队列或向量数据库。

### 12.2 外部依赖

- 数据源的可用性、服务条款和接口限流。
- DOI、ORCID、机构标识等外部标识质量。
- 数据源返回的引用关系和摘要完整度。
- 部署环境的 CPU、内存、磁盘和网络条件。

### 12.3 主要风险

| 风险 | 影响 | 初步应对 |
| --- | --- | --- |
| 数据源条款或接口发生变化 | 采集中断或合规风险 | 数据源合规台账、独立适配器、快速停用 |
| 页面结构变化 | 解析失败或字段错位 | 固定样例测试、字段缺失率监控 |
| 同名作者误合并 | 图谱结论失真 | 置信度分级、低置信度人工审核 |
| 双数据库同步失败 | 列表与图谱暂时不一致 | Outbox、幂等写入、重试和对账 |
| 图查询范围过大 | Neo4j 或浏览器负载过高 | 节点上限、深度上限、超时 |
| 数据规模超出建议基线 | 检索和任务吞吐下降 | 容量测试后再引入搜索引擎或队列 |
| 误用仓库中现有的 Neo4j 4.4 镜像 | 与已确认的 5.26 基线不一致，且缺少相应安全和维护支持 | 第一阶段固定使用 Neo4j 5.26 Community；现有 4.4 镜像不作为运行基线 |
